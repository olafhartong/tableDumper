# OpenGraph Export

`tableDumper --opengraph-export` writes a BloodHound OpenGraph payload next to the normal query response:

- `results.json`
- `results.opengraph.json`
- `results.opengraph.icons.json`

The generated file uses the minimal OpenGraph wrapper:

```json
{
  "graph": {
    "nodes": [],
    "edges": []
  }
}
```

The icon sidecar uses BloodHound's custom-node payload shape:

```json
{
  "custom_types": {
    "Machine": {
      "icon": {
        "type": "font-awesome",
        "name": "desktop",
        "color": "#2563EB"
      }
    }
  }
}
```

## Supported input shapes

The exporter is meant for graph-shaped Defender query results. It currently recognizes these result layouts:

- Alert-style nodes:
  - `id`, `type`, `label`, `properties`, `timestamp`
- Alert-style edges:
  - `sourceId`, `targetId`, `type` or `edgeType`, `label`, `properties`, `timestamp`
- ExposureGraph-style nodes:
  - `NodeId`, `NodeLabel`, `NodeName`, `Categories`, `NodeProperties`
- ExposureGraph-style edges:
  - `EdgeId`, `EdgeLabel`, `SourceNodeId`, `SourceNodeName`, `SourceNodeLabel`, `SourceNodeCategories`, `TargetNodeId`, `TargetNodeName`, `TargetNodeLabel`, `TargetNodeCategories`, `EdgeProperties`

If the query output does not look like one of those node or edge shapes, the exporter returns an error instead of guessing.

The exporter also supports a single mixed result set that contains both node rows and edge rows. Each row is classified independently, so a `union` query can populate both `graph.nodes` and `graph.edges` in one export.

## Pathfinding limitation

The files generated by `tableDumper` are generic OpenGraph payloads. BloodHound can ingest them, render them, and query them with Cypher, but they are not enough for BloodHound's pathfinding engine.

If you try to run a path query against these generic relationships, BloodHound can return `unsupported expansion direction`. That is expected because pathfinding support is tied to structured OpenGraph extensions with defined relationship semantics, not arbitrary imported edge kinds.

To use Pathfinding with imported data you need:

- a structured OpenGraph schema/extension installed in BloodHound
- relationship kinds modeled the way BloodHound expects for expansion
- a BloodHound deployment that supports structured OpenGraph features

If you only need exploration and filtering, use Cypher against the imported graph instead of the Pathfinding UI.

## Mapping rules

- Node IDs are copied into OpenGraph node `id`.
- Edge endpoints are emitted with `match_by: "id"` and the Defender source/target node ID as `value`.
- Node kinds come from Defender `type` or `NodeLabel`.
- ExposureGraph categories are appended as additional kinds when space is available.
- Edge kinds come from `edgeType`, `type`, or `EdgeLabel`.
- Kinds are sanitized to letters, numbers, and underscores.
  - Example: `has role on` becomes `has_role_on`.

## Property normalization

BloodHound OpenGraph expects lowercase property names and primitive values or arrays of primitive values. To fit that model, the exporter normalizes properties like this:

- Property names are lowercased.
- Nested objects are flattened with `_`.
  - Example: `rawData.severity` becomes `rawdata_severity`.
- Arrays of primitive values are preserved.
- Arrays or values that contain nested objects are JSON-stringified.
- Keys ending in `@odata.type` are dropped.
- `objectid` is reserved by BloodHound, so any incoming `objectId` field is renamed to `source_objectid`.

## Icons

BloodHound does not automatically know how to render arbitrary imported kinds. To handle that, `tableDumper` now writes `results.opengraph.icons.json` with a `custom_types` map keyed by exported kind name.

Default icon mappings are generated for the common kinds emitted by the alert graph exporter:

- `Alert` -> `triangle-exclamation`
- `User` -> `user`
- `Machine` -> `desktop`
- `File` -> `file`
- `Process` -> `gears`
- `Ip` -> `network-wired`
- `Url` -> `link`
- `CloudResource` -> `cloud`
- `MailMessage` -> `envelope`
- `Application` -> `window-maximize`

Unknown kinds fall back to `circle-question`.

Upload the icon file to BloodHound separately from the OpenGraph graph data. The payload is intended for `POST /api/v2/custom-nodes`.

## Direct upload

`tableDumper` can upload both generated artifacts directly to BloodHound when you provide:

- `--bloodhound-url`
- either `--bloodhound-token`
- or `--bloodhound-token-id` plus `--bloodhound-token-key`

Supported modes:

- `--bloodhound-upload-generated`
  - uploads the freshly generated `*.opengraph.json` file through BloodHound's file-upload job API
  - uploads the freshly generated `*.opengraph.icons.json` file through the custom-node API
- `--bloodhound-upload-file`
  - uploads an existing OpenGraph graph file
- `--bloodhound-upload-icons-file`
  - uploads an existing icon sidecar file

The icon upload is idempotent:

- new kinds are created with `POST /api/v2/custom-nodes`
- existing kinds are updated with `PUT /api/v2/custom-nodes/{kind}`

When you use `--bloodhound-token-id` and `--bloodhound-token-key`, `tableDumper` signs each request using BloodHound's HMAC request-signing scheme instead of sending a bearer token.

## Edge-only exports

`ExposureGraphEdges` rows contain enough source and target node metadata for the exporter to synthesize endpoint nodes in the same OpenGraph payload.

`AlertEdges` rows only expose source and target IDs, so the exporter writes edges only. If you want the corresponding nodes in BloodHound, export the matching node query as well.

## Cypher query note

For the alert graph in this repo, edges are exported as directed relationships from the alert node to the evidence/entity node:

- `Alert -> User`
- `Alert -> Machine`
- `Alert -> File`
- `Alert -> Process`

When writing BloodHound Cypher for multi-hop traversal, use explicit directed expansion on those edges. BloodHound's supported Cypher syntax documents recursive expansion with a directed arrow such as `-[:MemberOf*..]->`, rather than undirected expansion. Single-hop incoming patterns are supported, but for recursive traversal and shortest-path style queries you should keep the expansion directed.

Example patterns:

```cypher
MATCH p = (:Alert)-[:AlertImpacted|AlertRelated|AlertSource|AlertDestination*1..4]->(n)
RETURN p
LIMIT 100
```

```cypher
MATCH (n {id: "your-node-id"})<-[:AlertImpacted|AlertRelated|AlertSource|AlertDestination]-(a:Alert)
RETURN a, n
LIMIT 100
```

If a query uses undirected or unsupported recursive expansion, BloodHound can return `unsupported expansion direction`.
